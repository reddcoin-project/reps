## 1. Abstract

[REP-0003](rep-0003.md) closes the stake-grinding **capture** vector (median-of-11
lockout + honest-invisible future winners) and, with wallet search parity, removes
the honest/attacker fairness gap. One residual remains: Reddcoin's stake modifier
is **coin-fixed** - derived once from the coin's own block (`GetKernelStakeModifier`,
`src/pos/kernel.cpp:273-353`) - so for a given UTXO the modifier is
**precomputable arbitrarily far in advance**.

This REP removes that residual *cryptographically* by replacing the legacy (coin-fixed)
modifier with a **per-block, prevout-bound modifier** rolled forward every block,
exactly as in the two chains that fully resolved this class:

- **Blackcoin PoSV3:** `nStakeModifier = Hash(kernel || prevModifier)` (`pos.cpp:32-38`)
- **PIVX stakeModifierV2:** `Hash(coinstake.prevout || prevModifier)` (`chain.cpp`)

Reddcoin already stores each block's coinstake prevout on the block index
(`CBlockIndex::prevoutStake`, `chain.h:219`), so the PIVX-style prevout-bound form
drops in cleanly:

```
pindex->nStakeModifierV2 = Hash( pindex->prevoutStake || pprev->nStakeModifierV2 )
```

and the kernel, once active, hashes `pindexPrev->nStakeModifierV2` instead of the
coin-fixed value. Because a block a new node accepts has a *different*
`hashProofOfStake` under the old modifier, old nodes reject it - this is a
**hard fork** (bilateral), and therefore cannot ride REP-0003's BIP9 soft fork.

Together, REP-0003 (timestamp mask + drift) and REP-0004 (per-block modifier) give
Reddcoin the full Blackcoin-grade **PoSV3 kernel**, while **retaining Reddcoin's
PoSV coin-age weight** (unlike Blackcoin/PIVX, which dropped coin age). Net result:
the attacker's advantage over an honest staker goes from ~7,200x (pre-REP-0003) to
~1x (post-REP-0003) to **cryptographically ~1x with zero precomputation value**
(post-REP-0004).

## 2. Motivation

### 2.1 The residual after REP-0003
Post-REP-0003 the legal window per tip is `[median+1, now+15s]` at 16-second
granularity - roughly **~20 masked slots**, essentially all in the past half. With
wallet search parity (R5) honest stakers enumerate the same ~20 slots, so there is
no *fairness* gap. But the modifier for a given UTXO is still fixed the moment the
coin buries, so an attacker can **precompute** the kernel outcome of every slot for
every UTXO, indefinitely ahead. That precomputation buys little once the window is
20 slots recomputed every ~60 s - but it is a standing cryptographic weakness and
the last structural difference from the fully-resolved chains.

### 2.2 What a per-block modifier changes
With `nStakeModifierV2` rolled forward each block and bound to that block's own
coinstake prevout, the modifier for a stake at tip `T` is unknown until `T` exists.
Precomputation across tips is impossible; each new block fully re-randomizes the
search. This is the property Blackcoin and PIVX rely on.

### 2.3 Simplification bonuses
Adopting a rolling per-block modifier also **retires** two fragile pieces of the
legacy machinery for post-activation blocks:

- The `GetKernelStakeModifier` selection walk (`kernel.cpp:273-353`) and the
  `GetLastStakeModifier` reindex-compat fallback whose ambiguity already caused the
  v4.22.9/v4.22.10 divergence (`kernel.cpp:73-85`). The per-block modifier is a plain hash
  chain with no interval/selection ambiguity.
- The offline modifier reconstruction used by the disclosure tooling
  (`build_chain_table.py`, ~200 lines of selection logic - it lives with the stake-grinding
  PoC, **not** in `reddcoin-project/reddcoin`) becomes a trivial rolling hash for
  post-activation blocks.

## 3. Specification

Let activation be the buried deployment `DEPLOYMENT_POSV3MOD` at height
`H = consensus.POSV3ModHeight`. Define
`PoSV3ModActive(pindexPrev) := DeploymentActiveAfter(pindexPrev, params, DEPLOYMENT_POSV3MOD)`.

**M1 - Per-block modifier (state).** For every PoS block at height `>= H`, on
connect:
```
pindex->nStakeModifierV2 = Hash( pindex->prevoutStake || pprev->nStakeModifierV2 )
```
At the activation block, `pprev->nStakeModifierV2` is seeded to `uint256(0)`
(genesis-style seed, as PIVX does at its upgrade block). `nStakeModifierV2` is a new
`uint256` field on `CBlockIndex`, persisted in `CDiskBlockIndex`.

**M2 - Kernel (consensus).** When `PoSV3ModActive(pindexPrev)`, `CheckStakeKernelHash`
computes:
```
hashProofOfStake = Hash( pindexPrev->nStakeModifierV2
                         || nTimeBlockFrom || prevout.hash || prevout.n
                         || nTimeTxPrev || nTimeTx )
pass  iff  hashProofOfStake <= bnTargetPerCoinDay * bnCoinDayWeight
```
The target/weight comparison is **unchanged** - Reddcoin's PoSV coin-day weight
(`GetCoinAgeWeight`, `kernel.cpp:47-63`) is retained. Only the modifier source
changes (the per-block modifier instead of the legacy coin-fixed modifier) and the preimage adopts
`prevout.hash` (dropping the legacy `nTxPrevOffset`-equals-vout-index quirk).

**M3 - Below activation.** Blocks at height `< H` validate with the existing legacy
kernel and modifier, unchanged. Non-retroactive.

**M4 - Coin age retained.** Coin-day weight, `nStakeMinAge`/`nStakeMaxAge`, and the
PoSV reward curve are untouched. This REP is strictly a modifier/preimage change.

### 4.2 `src/chain.h` - new index field + serialization
```cpp
    uint64_t nStakeModifier{0};            // legacy modifier (historical + pre-activation)
    uint256  nStakeModifierV2{};           // REP-0004: per-block rolling modifier
    ...
    void SetStakeModifierV2(const uint256& m) { nStakeModifierV2 = m; }
```
`CDiskBlockIndex` (`chain.h:412-443`) - persist the field behind a client/index
version gate so old indexes remain readable during migration. The serializer already
captures the writing client's version into a local named **`_nVersion`** at `:414`:
```cpp
    SERIALIZE_METHODS(CDiskBlockIndex, obj)
    {
        int _nVersion = s.GetVersion();                                    // :414, existing
        if (!(s.GetType() & SER_GETHASH)) READWRITE(VARINT_MODE(_nVersion, VarIntMode::NONNEGATIVE_SIGNED));
        ...
        READWRITE(obj.nStakeModifier);                                     // :436
        // REP-0004: gate on the *record's* client version, captured above.
        if (_nVersion >= INDEX_V3_MODIFIER && obj.IsProofOfStake())
            READWRITE(obj.nStakeModifierV2);
        READWRITE(obj.hashProofOfStake);                                   // :437
```
> **Use `_nVersion`, not `nVersion`.** There is no identifier called `nVersion` in
> this scope, and `obj.nVersion` is the **block header version** (`:425`) - currently
> 5 for every PoS block. Gating on `obj.nVersion` would compile and then read the new
> field for every block ever written, corrupting the index. `_nVersion` is round-
> tripped through the record itself (`:415`), so on read it holds the `CLIENT_VERSION`
> that wrote that entry - which is exactly the gate wanted here. The block index db
> streams are constructed with `CLIENT_VERSION` (`dbwrapper.h:64`), so bumping
> `CLIENT_VERSION` is what moves the gate.
>
> The `&& obj.IsProofOfStake()` conjunct mirrors the existing treatment of
> `prevoutStake` / `nStakeTime` (`:438-442`), which are already PoS-only. A per-block
> stake modifier is meaningless on a PoW-era block, and skipping it keeps the record
> layout consistent with the fields it is derived from.

### 4.3 `src/validation.cpp` - compute in `AcceptBlock` (`:3712-3717`)

The existing legacy modifier is computed in **`CChainState::AcceptBlock()`**
(defined `:3640`), not in `ConnectBlock`. The per-block modifier rolls in the same
place, immediately after it:
```cpp
    // existing legacy modifier compute stays for history/pre-activation (:3712-3717):
    uint64_t nStakeModifier = 0;
    bool fGeneratedStakeModifier = false;
    if (!ComputeNextStakeModifier(this, pindex, nStakeModifier, fGeneratedStakeModifier)) { ... }
    pindex->SetStakeModifier(nStakeModifier, fGeneratedStakeModifier);

    // REP-0004: roll the per-block modifier once active.
    if (pindex->IsProofOfStake() && DeploymentActiveAfter(pindex->pprev, params, Consensus::DEPLOYMENT_POSV3MOD)) {
        CHashWriter ss(SER_GETHASH, 0);                   // <hash.h>, already included (validation.cpp:21)
        ss << pindex->prevoutStake;                       // already stored on the index (chain.h:219)
        ss << (pindex->pprev ? pindex->pprev->nStakeModifierV2 : uint256());
        pindex->SetStakeModifierV2(ss.GetHash());
    }
```
> **Acceptance, not connection - and this is the right stage.** Because the modifier
> depends only on the block's own `prevoutStake` and its parent's modifier, it is
> branch-independent: computing it at acceptance populates it for every block admitted
> to the index, including blocks on branches that are never connected. The kernel
> reads `pindexPrev->nStakeModifierV2`, and a parent is always accepted before its
> child, so the value is present whenever it is needed.
>
> It also determines the migration path (§4.6/§5): a field written in `AcceptBlock`
> and stored on `CDiskBlockIndex` is **not** repopulated by `-reindex-chainstate`.

### 4.6 Version / migration plumbing
- Bump the block-index db version (`CLIENT_VERSION`) so upgraded nodes know to
  compute/populate `nStakeModifierV2` from `H` forward; that is the value `_nVersion`
  gates on in §4.2.
- Simplest correct migration: on first start of an upgraded node whose chain is
  already past `H`, require/trigger a **full `-reindex`**. Document in release notes.

> **Not `-reindex-chainstate`.** The two are not interchangeable here.
> `-reindex-chainstate` is documented as "Rebuild chain state from the **currently
> indexed blocks**" (`init.cpp:415`); its wipe flag applies to the coins view
> (`init.cpp:1435`), and the block-index rebuild is governed separately by
> `fReset = fReindex` (`init.cpp:1361`). It replays connection over the *existing*
> block index and never re-runs `AcceptBlock`, which is where §4.3 populates
> `nStakeModifierV2`. A node migrated with `-reindex-chainstate` would therefore come
> up with an empty per-block modifier on every pre-existing index entry and fail every
> post-`H` kernel check. Full `-reindex` rebuilds the index from the block files and
> re-runs `AcceptBlock`, so it does repopulate the field.

## 5. Migration & reindex (the hard part)

- **Index format change.** `nStakeModifierV2` adds a serialized field. Old clients
  cannot read the new index - acceptable (hard fork; all nodes upgrade). New clients
  read old indexes via the version gate (§4.2) and populate the per-block modifier lazily from `H`.
- **Recompute path.** The per-block modifier chain is deterministic from `H`
  (`seed 0 -> roll`). A full **`-reindex`** reproduces it exactly - not
  `-reindex-chainstate`, which reuses the existing block index and never re-runs the
  `AcceptBlock` code that populates the field (§4.6). A lighter one-time forward pass
  from `H` over the loaded index is a possible optimization, and is attractive here
  precisely because the rolling formula needs only `prevoutStake` and the parent's
  modifier - both already on the index - so it does not require re-reading block
  files. Full `-reindex` remains the guaranteed-correct baseline for the first release.
- **No historical divergence.** Pre-`H` blocks keep the legacy kernel/modifier, so the
  existing chain and all historical proofs validate unchanged; there is no reorg of
  history. Unlike the legacy `GetLastStakeModifier` fallback, the per-block modifier chain has a single
  deterministic definition - no cross-version ambiguity.
- **Offline tooling.** `build_chain_table.py`-style reconstruction (external to this
  repository - see §2.3) for post-`H` blocks reduces to `Hash(prevout || prevMod)`;
  keep the legacy reconstruction only for pre-`H` history.

## 6. Unit tests - `src/test/pos_modifier_v3_tests.cpp` (new)
- **Rolling determinism:** given a fixed sequence of `prevoutStake`, the per-block modifier chain is
  reproducible; changing any one prevout changes all subsequent modifiers.
- **Seed:** activation block seeds from `uint256(0)`.
- **Kernel divergence:** for one coinstake, `hashProofOfStake` under the per-block modifier differs from
  the legacy value (proves the hard-fork incompatibility at the unit level).
- **Coin-age intact:** `GetCoinAgeWeight` / target comparison unchanged across the
  branch (same weight in/out).
- **Gate:** below `H` uses the legacy modifier, at/above `H` uses the per-block modifier (custom-params `CBlockIndex`
  chain, mirroring `versionbits_tests` fixtures).

## 7. Functional tests - `test/functional/`
- **`feature_posv3mod_activation.py`:** mine across `H`; assert post-`H` blocks carry
  a populated `nStakeModifierV2` (via a debug RPC / `getblock` extension) and that
  the modifier changes every block and depends on the coinstake prevout.
- **`feature_posv3mod_hardfork_split.py` (key):** two nodes, one at the REP-0004
  release and one pre-fork. Mine a post-`H` block on the upgraded node; assert the
  **pre-fork node rejects it** (different `hashProofOfStake` -> `high-hash`/stake
  check failure) and the chains split at `H` - proving the bilateral hard fork.
- **`feature_posv3mod_stakegrind.py`:** re-run the REP-0003 anti-grind suite and
  additionally assert the **precompute residual -> 0**: a modifier computed for tip
  `T` does not predict the winning set at tip `T+1` (modifier re-randomizes), i.e. a
  block precomputed against `T`'s modifier fails once the tip advances.
- **`feature_posv3mod_reindex.py`:** `-reindex` past `H` reproduces identical
  `nStakeModifierV2` values and the same best chain (determinism). The test should
  **also** assert the negative: a node restarted with only `-reindex-chainstate` does
  *not* repopulate the field (§4.6), so that the release notes' choice of flag is
  covered by CI rather than by prose alone.

## 8. Fork implications - bilateral HARD fork
- **Why hard:** the stake modifier is an input to the kernel hash but is supplied by the
  validator from chain state, not carried in the coinstake. Old nodes inject the
  **legacy modifier** (coin-derived); new nodes inject the block's **per-block modifier**
  (`nStakeModifierV2`). For a byte-identical coinstake these differ, so `hashProofOfStake`
  differs entirely (SHA-256d avalanche) - a proof that meets the target under the legacy
  modifier fails under the per-block modifier, and vice versa. New-rule blocks fail the old
  kernel and old-rule blocks fail the new one -> old and new nodes reject each other's blocks
  -> clean bilateral split at `H`. No shared valid-block subset, so it cannot be a soft fork
  or use versionbits/BIP9.
- **Activation:** fixed **height flag day** (`POSV3ModHeight`), announced well ahead;
  **mandatory upgrade** for all nodes, pools, exchanges, and stakers. Add a
  **checkpoint** at (or shortly after) `H` to seal the transition against deep reorg.
- **No signaling:** unlike REP-0002/0003, readiness is coordinated off-chain
  (release + comms), because non-upgraded nodes fork off regardless of any signal.
- **Non-retroactive:** history (pre-`H`) validates unchanged; no reorg of the
  existing chain is caused by the upgrade itself.

## 9. Deployment & rollout
1. Land REP-0002 + REP-0003 first; let REP-0003 (PoSV3 timestamps) activate and bury.
2. Merge REP-0004 with `POSV3ModHeight = NEVER` on mainnet; active on regtest,
   scheduled on testnet; run all suites through a testnet fork + reindex.
3. Set mainnet `POSV3ModHeight` a comfortable margin above the current tip; publish
   the mandatory-upgrade notice and the activation height.
4. Ship the same release to exchanges/pools/stakers; confirm upgrade before `H`.
5. At `H`: PoSV3 kernel activates; checkpoint the transition; monitor for a minority
   pre-fork chain and orphan behaviour.

## 10. Backwards compatibility
- **Consensus:** breaking for all non-upgraded nodes at `H` (intended, hard fork).
- **Index/db:** format bump; upgraded nodes migrate via a full `-reindex`
  (**not** `-reindex-chainstate` - see §4.6).
- **RPC:** optionally expose `nStakeModifierV2` in `getblock`/`getblockheader` for
  observability and tooling; `modifier` (legacy) remains for historical blocks.
- **History/explorers:** pre-`H` unchanged; explorers computing modifiers must switch
  to the rolling formula at `H`.
