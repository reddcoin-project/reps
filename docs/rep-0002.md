- **Target:** `reddcoin-project/reddcoin` develop (`87df3a9`).
- **Enables:** [REP-0003](rep-0003.md) (PoSV3 stake-timestamp soft fork) and any future

---

## 1. Abstract

Reddcoin's deployment state machine is BIP9 (`src/versionbits.cpp`): a deployment
that fails to reach the signaling threshold before `nTimeout` transitions to
`FAILED` and never activates. That is the wrong failure mode for a **security**
fix, which must activate by a known deadline regardless of staker apathy or
dormant/abandoned stake that dilutes signaling.

This REP adds **BIP8 `lockinontimeout` (lot=true)**: a per-deployment boolean
that, when set, makes a `STARTED` deployment transition to `LOCKED_IN` at
`nTimeout` (then `ACTIVE`) instead of `FAILED`. It still activates *early* if the
threshold is met, so it is signal-gated when stakers are ready and
deadline-guaranteed otherwise - a built-in flag day that early signaling can only
bring forward, never cancel. Two lot=true modes are available: the default
**minimal** mode simply locks in at the deadline, and an opt-in **MUST_SIGNAL**
mode additionally forces the signal bit during the final period so the chain
demonstrably signals before lock-in (§5).

The change **defaults to `false`** and no existing deployment sets it, so it is
**byte-for-byte behavior-identical** to today until a deployment opts in. It is
therefore safe to merge ahead of any consumer. Its first consumer is
DEPLOYMENT_POSV3 ([REP-0003](rep-0003.md)).

---

## 2. Motivation

- **BIP9 can silently fail.** `GetStateFor`'s `STARTED` case
  (`versionbits.cpp:75-79`) goes `FAILED` at timeout if `count < nThreshold`. On an
  old PoS chain a large fraction of stake may be dormant (lost keys, offline
  wallets) and can never signal, so a 90-95 % threshold may be unreachable even
  with unanimous *active* staker support. A security fix stuck in `FAILED` is a
  non-outcome.
- **Flag-day alone loses the early-adoption benefit.** A pure height/time flag day
  activates on a fixed date with no way for a ready supermajority to pull it
  forward, and no on-chain readiness signal.
- **BIP8 lot=true is the standard resolution.** Keep BIP9 signaling, but guarantee
  lock-in at the deadline. This gives the best of both: activate as soon as the
  threshold is met, and no later than `nTimeout`.

---

## 3. Specification

Add two per-deployment flags - `BIP9Deployment.lockinontimeout` and
`BIP9Deployment.mustsignal` (both default `false`). Modify the versionbits
threshold state machine's `STARTED` transition, add an optional `MUST_SIGNAL`
state, and (only for deployments that set `mustsignal`) enforce signaling during
that state:

```
STARTED, at end of a period:
    if   count >= threshold                          -> LOCKED_IN      (unchanged)
    elif MedianTimePast >= nTimeout:
             if !lockinontimeout                      -> FAILED         (unchanged, BIP9)
             elif mustsignal                          -> MUST_SIGNAL    (NEW: full BIP8 lot=true)
             else                                     -> LOCKED_IN      (NEW: minimal lot=true)
MUST_SIGNAL (one period) -> LOCKED_IN                                   (NEW)
    (during this period, non-signaling blocks are INVALID - §4.5)
LOCKED_IN -> ACTIVE at min_activation_height          (unchanged)
```

With `lockinontimeout=false` the machine is identical to BIP9. With
`lockinontimeout=true, mustsignal=false` (the recommended default) it gains only
the timeout->LOCKED_IN edge. `mustsignal=true` additionally introduces the
`MUST_SIGNAL` state and its block-signaling rule (§4.5). All other states,
caching, and per-period computation are unchanged.

**Scope / default.** The **recommended default** is minimal lot=true
(`lockinontimeout=true, mustsignal=false`): guaranteed lock-in at timeout, no
block-rejection logic. `MUST_SIGNAL` is fully specified but **opt-in** per
deployment; §5 compares the two and says when each is appropriate. A deployment
that leaves both flags false is plain BIP9.

**Determinism / network requirement.** The lot=true value for a given deployment
is fixed in the release (chainparams). All nodes validating the transition must run
the same value, or lot=true nodes (`LOCKED_IN`) and lot=false/legacy nodes
(`FAILED`) would diverge. This is satisfied because a deployment's `lockinontimeout`
ships in the same release as the deployment itself.

### 4.5 `src/validation.cpp` - MUST_SIGNAL block enforcement (only if `mustsignal`)

A deployment that opts into `mustsignal` needs one extra consensus rule: during its
`MUST_SIGNAL` period every block must signal the deployment's bit, or the block is
invalid.

Signalling must be tested exactly as `VersionBitsConditionChecker::Condition`
(`versionbits.cpp:181-184`) defines it - the top bits **and** the deployment bit.
Testing the bit alone would accept a block that the threshold counter does not count
as signalling, so the rule and the counter would disagree.

Place it in `ContextualCheckBlockHeader` (`validation.cpp:3353`): this is a
header-only property, and rejecting there avoids downloading and validating the body
of a block that cannot be valid. That function receives `const CChainParams& params`,
so the consensus params come from `params.GetConsensus()`:
```cpp
    // REP-0002: enforce forced signalling during a deployment's MUST_SIGNAL period.
    const Consensus::Params& consensusParams = params.GetConsensus();
    for (int i = 0; i < (int)Consensus::MAX_VERSION_BITS_DEPLOYMENTS; ++i) {
        const auto dep = Consensus::DeploymentPos(i);
        if (!consensusParams.vDeployments[dep].mustsignal) continue;
        if (g_versionbitscache.State(pindexPrev, consensusParams, dep) != ThresholdState::MUST_SIGNAL) continue;
        const bool signals = ((block.nVersion & VERSIONBITS_TOP_MASK) == VERSIONBITS_TOP_BITS) &&
                             (block.nVersion & VersionBitsCache::Mask(consensusParams, dep)) != 0;
        if (!signals) {
            return state.Invalid(BlockValidationResult::BLOCK_INVALID_HEADER, "must-signal",
                strprintf("block does not signal bit %d during MUST_SIGNAL",
                          consensusParams.vDeployments[dep].bit));
        }
    }
```
> API notes for this tree (Bitcoin Core v0.22 lineage): versionbits is reached through
> the `VersionBitsCache` class, not the pre-0.21 free functions. `State()` is a member
> on the global `g_versionbitscache` (declared `deploymentstatus.h:14`); `Mask()` is a
> **static** member. `ContextualCheckBlockHeader` already holds `cs_main`, which is
> what `State()` requires. If the rule is instead placed in `ContextualCheckBlock`
> (`validation.cpp:3399`), that function receives `const Consensus::Params&` directly
> and the `GetConsensus()` line is dropped.

This is the **only** block-rejection path `mustsignal` adds; with `mustsignal=false`
(default) it is never reached. It is self-limiting: it fires for exactly the one
MUST_SIGNAL period, after which the deployment is `LOCKED_IN` and the rule stops.

### 4.6 `src/rpc/mining.cpp` - `getblocktemplate` (required for `mustsignal`)

§4.5 makes such blocks invalid. `MUST_SIGNAL` therefore belongs on the force-set path:

> Pushing the rule name into `aRules` (rather than `vbavailable`) tells a GBT client

## 5. Activation policy - minimal lot=true (default) vs MUST_SIGNAL (opt-in)

Both modes are specified; a deployment selects one via its flags:

| Mode | Flags | Timeout behavior | Adds block-rejection? |
|---|---|---|---|
| BIP9 | `lot=false` | FAILED (never activates) | no |
| Minimal lot=true (**default**) | `lot=true, mustsignal=false` | STARTED -> LOCKED_IN | no |
| Full BIP8 (**opt-in**) | `lot=true, mustsignal=true` | STARTED -> MUST_SIGNAL -> LOCKED_IN | yes, one period (§4.5) |

| | Minimal (default) | MUST_SIGNAL (opt-in) |
|---|---|---|
| Guarantees activation by `nTimeout` | yes | yes |
| Forces final-period blocks to signal | no | yes |
| Adds a `MUST_SIGNAL` state + block-rejection rule | no | yes (larger surface) |
| Risk / review cost | low | higher |

**Recommendation: default to minimal.** The property a security fix needs is *"the
rule is enforced by a known date,"* which minimal lot=true already delivers - once
`ACTIVE`, the consuming deployment's rules apply to every block regardless of whether
pre-activation blocks signaled.

**When to choose MUST_SIGNAL.** Use it when observers must be able to infer
activation from on-chain signaling (lightweight clients, cross-chain watchers, or
miners/stakers that gate behavior on the bit), or to make the final period visibly
demonstrate near-unanimous readiness. The cost is the extra consensus state and the
temporary block-rejection rule (§4.5), which briefly orphans non-signaling stakers'
blocks during that one period. [REP-0003](rep-0003.md) (PoSV3) uses **minimal**; MUST_SIGNAL is
available for future deployments that want enforced signaling.

> `nVersion` from `ComputeBlockVersion` (`miner.cpp:157`), which sets the bit while
> STARTED. The essential assertion is: identical non-signaling chain -> lot=true node
> reaches `active=True` at/after timeout, lot=false node does not.
> `test/functional/feature_versionbits_warning.py` is the existing versionbits
> functional test in this tree and is the closest model for driving a node with
> hand-built block versions.

**MUST_SIGNAL variant.** For a deployment with `mustsignal=true`
(`-vbparams=posv3:START:END:0:1:1`), add a case that submits a **non-signaling**
block during the MUST_SIGNAL period (bit 5 cleared via raw `create_block`) and asserts
it is rejected with `must-signal` (§4.5); then a signaling block is accepted and the
deployment reaches `LOCKED_IN`/`ACTIVE`. This exercises the one block-rejection path
`mustsignal` adds - the minimal-mode test above must show no such rejection.

**Block-production regression (§4.3 / §4.6).** The above tests drive the node with
externally built blocks, so they do not exercise the paths that build blocks. Add two
assertions that would otherwise fail silently:

* With a `mustsignal` deployment in `MUST_SIGNAL`, `getblocktemplate`'s returned
  `version` must have bit 5 set, and the deployment must appear in `rules` rather than
  `vbavailable` (§4.6).
* A block produced by the node's own miner during `MUST_SIGNAL` must be accepted by
  its own §4.5 rule - the direct regression test for the `ComputeBlockVersion` change
  (§4.3). Without it, a `mustsignal` deployment makes a staking node orphan its own
  blocks, and no unit test or compiler diagnostic catches it.

## 8. Fork / compatibility implications

- **Not an activation by itself.** With `lockinontimeout=false` everywhere (the
  default, and the state of every current deployment), `GetStateFor` returns
  identical results to today. Zero consensus effect on merge.
- **The consumer carries the fork.** Any network effect arises only when a
  deployment sets `lockinontimeout=true` ([REP-0003](rep-0003.md)). The soft/hard-fork character
  is that of the *consuming* deployment, not of this mechanism.
- **Uniform-release requirement.** Because lot=true vs lot=false yields divergent
  states (`LOCKED_IN` vs `FAILED`) at timeout, the value must ship in the release
  the whole network runs for that deployment - the normal expectation for a
  consensus release. Nodes without this code (older than REP-0002) would compute
  `FAILED` for a lot=true deployment and split at the timeout period; therefore a
  lot=true deployment MUST require nodes at or above the REP-0002 release
  (enforced socially + by [REP-0003](rep-0003.md)'s rollout timeline).
- **Non-retroactive.** No change to any historical deployment's computed state
  (all are lot=false). No reindex/reorg implication.
- **`mustsignal` adds a temporary rule.** A deployment that opts into `mustsignal`
  carries one consensus block-rejection rule (§4.5) that fires only during its
  MUST_SIGNAL period - a self-limiting, soft-fork-style tightening on top of the
  mechanism. With `mustsignal=false` (default, and REP-0003's choice) that path
  never exists.

1. Merge REP-0002 (inert; default false). CI green; all existing versionbits unit
   and functional tests pass unchanged.
2. Release as part of the same client version that carries [REP-0003](rep-0003.md) (so any
   lot=true deployment and the code that honors it ship together).
3. No standalone activation - this REP has none.

## 10. Relationship to other REPs
- **[REP-0003](rep-0003.md) (PoSV3 soft fork)** sets `vDeployments[DEPLOYMENT_POSV3].lockinontimeout
  = true` (with `mustsignal=false` - the minimal mode), consuming this mechanism to
  guarantee the security fix activates by its deadline. [REP-0003](rep-0003.md) depends on REP-0002 being merged first.
- **REP-0004 (per-block modifier hard fork)** does not use versionbits at all
  (hard fork, height/flag-day activation), so it is unaffected by this REP.
